# System Architecture

## Overview

The Vehicle Physics Digital Twin Platform is a web-based simulation and
analysis tool for comparing internal-combustion (ICE), hybrid, and
battery-electric (BEV) vehicles under a shared physical framework. All
three powertrains are built on top of the same longitudinal vehicle
dynamics core, so differences in simulated behavior come only from the
powertrain itself, not from inconsistent physics.

│ ├── main.py # FastAPI app entry point, CORS, router registration

│ │ ├── vehicles.py # Single-point physics check
│ │ ├── simulation.py # Drive-cycle simulation (Vehicle Dynamics, ICE, BEV, Hybrid)
│ │ ├── analysis.py # Energy flow breakdown per powertrain
│ │ ├── validation.py # Real-data upload and model-vs-real comparison
│ │ └── comparison.py # Unified ICE vs Hybrid vs BEV comparison
│ ├── models/ # Domain objects (fixed parameters + state)
│ │ ├── vehicle.py # Vehicle body parameters
│ │ ├── ice.py # ICE powertrain (engine + transmission)
│ │ ├── motor.py # Electric motor + inverter
│ │ ├── battery.py # Battery pack (SOC + optional thermal state)
│ │ ├── bev.py # BEV powertrain (motor + battery)
│ │ └── hybrid.py # Hybrid powertrain (ICE + motor + battery + controller)
│ ├── physics/ # Pure physics equations, no simulation state
│ │ ├── longitudinal.py # Rolling, aero, grade, acceleration forces
│ │ ├── drivetrain.py # Gear ratio / angular velocity / torque conversions
│ │ ├── energy.py # Fuel power <-> fuel volume conversions
│ │ └── thermal.py # Lumped thermal model (dT/dt = P_loss - hA*dT)
│ ├── simulation/ # Time-domain simulation engines
│ │ ├── drive_cycle.py # Drive cycle representation (time, speed, acceleration)
│ │ ├── standard_cycles.py # Built-in synthetic test cycle
│ │ ├── real_data.py # CSV parsing for real-world vehicle data
│ │ ├── solver.py # Pure vehicle dynamics simulation (no powertrain)
│ │ ├── ice_simulation.py # Vehicle dynamics + ICE powertrain
│ │ ├── bev_simulation.py # Vehicle dynamics + BEV powertrain
│ │ └── hybrid_simulation.py # Vehicle dynamics + Hybrid powertrain
│ └── analysis/ # Post-processing and cross-powertrain analysis
│ ├── metrics.py # Energy breakdown per powertrain (input -> useful -> losses)
│ ├── validation.py # MAE / RMSE / max error / bias vs real data
│ └── comparison.py # Runs all three powertrains under identical conditions
└── tests/ # pytest suite, one file per module/phase

No frontend framework is used intentionally: plain HTML/CSS/JS plus
Chart.js (loaded from CDN) keeps the platform simple to run and makes
the frontend-backend boundary explicit, which is itself part of the
engineering demonstration.

|

|
v

|

## Local Development

- `start.sh` launches the backend (`uvicorn`) and frontend (`python -m http.server`)
  as detached background processes, auto-selects free ports to avoid
  conflicting with other projects, writes `frontend/js/config.js` with
  the actual backend port, and opens the homepage in the browser.
- `stop.sh` reads the saved PID files and stops both processes.
- Logs are written to `.run/logs/backend.log` and `.run/logs/frontend.log`.

## Design Principles

1. **One shared physics core.** ICE, Hybrid and BEV are not three
   separate simulators; they are three powertrain implementations
   plugged into the same `Vehicle` + `Environment` + `DriveCycle`
   framework (see `physics_model.md`).
2. **Separation of concerns.** `physics/` contains stateless equations;
   `models/` contains parameter + state objects; `simulation/` orchestrates
   them over time; `analysis/` post-processes results; `api/` only
   translates HTTP <-> domain objects.
3. **Backward compatibility across phases.** Each phase adds new
   modules and endpoints without breaking earlier ones (e.g. `/run`
   from Phase 2 still works after `/run-ice`, `/run-bev`, `/run-hybrid`
   were added).
4. **No premature complexity.** Efficiency maps, gear shifting, and
   detailed combustion models are deliberately out of scope for V1;
   the platform is designed so they can be added later without
   restructuring the core.
